1. Opening and purpose

~40 sec

Title slide, then the project workflow.

Good morning, ma’am. Our project is an Urban Mobility Database for traffic analysis using Advanced SQL. The main problem we address is that traffic data becomes difficult to interpret when it is left as a flat file. We designed a relational MySQL database, a repeatable import process, SQL analyses, and a website that presents the results. We also built a separate synthetic junction experiment to compare two signal-control strategies.

For this review, I will show the data source, the database design, how the analysis reaches the website, the SQL features we implemented, and what has been verified so far. I will keep the historical dataset and generated simulation results clearly separate.

2. Dataset and its limits

~55 sec

Dataset slide or Data & Provenance screen.

We selected the Bangalore Traffic 2023–2024 CSV from Kaggle. The file we inspected contains 33,072 data rows and 18 source columns. It covers dates from 1 January 2023 through 9 August 2024, eight areas, sixteen road locations, and six named time blocks. Important fields include area, road or intersection name, date, traffic volume, reported average speed, congestion level, weather, and roadwork.

This file contains aggregate observations. It does not identify individual vehicles or trips, give road coordinates, or provide exact timestamps within a day. The measurement units and collection method are not documented in the file. We therefore use the source’s labels honestly: for example, “reported volume” rather than “unique vehicles,” and “Morning” as a category rather than a clock-hour interval.

3. End-to-end design

~45 sec

Workflow diagram or website navigation.

The historical-data flow is CSV, then validation and normalization, then MySQL tables and views, then server-side queries, and finally the website dashboard and reports. A separate simulation flow generates a repeatable sequence of vehicles, changes virtual signal phases, writes its own MySQL records, and displays the measured results. This separation prevents synthetic vehicles from being mistaken for historical Bangalore observations.

The website is built with Next.js and React. Its API uses the MySQL driver to execute parameterized SQL. MySQL Workbench connects to the same local database, so we can inspect the rows and query results independently of the website.

4. Relational database design

~1 min

Schema Explorer or Workbench table list and foreign keys.

The schema defines fourteen tables in total. Ten support historical data and application state; four support the simulation. The main historical relationship is Area to Road to Road Segment to a logical Sensor location to Traffic Observation. Separate tables hold import metadata, the selected active import, and a daily summary. Primary keys identify records, foreign keys preserve the relationships, and checks constrain values such as nonnegative counts and allowed congestion categories.

We included Vehicle and Trip as extension tables because they were part of the original proposed model. They should remain empty for this CSV: one aggregate row cannot be turned into real vehicle identities or a real trip. Our Sensor identifiers are likewise logical labels for source locations, not claims that physical devices were present.

5. Data preparation, import, and quality

~1 min

Data & Provenance page, importer report, then a Workbench count if available.

The import code reads the CSV, checks required columns, validates every row, and maps source fields into normalized columns. It retains all original source values in JSON so that a database result can be traced back to the CSV. It records a SHA-256 fingerprint of the file, counts accepted and rejected rows, and uses a transaction when activating an import. Loading the same file again reuses its recorded import rather than silently duplicating the dataset.

In our local file inspection, all 33,072 rows passed the validator and no exact duplicate rows were found. 7. Advanced SQL exercises

~1 min 20 sec

SQL Query Lab; run “Busiest roads,” “Daily road ranking,” and “Change since previous observed date.”

The SQL Lab contains eleven saved, read-only exercises. It is deliberately curated rather than an unrestricted SQL editor. 9. Index and query-plan comparison

11. Synthetic traffic-signal experiment

~1 min 20 sec

Live Simulation page; run one surge scenario with seed 42 if verified.

The simulation is a separate, deterministic four-way junction model. It generates arrivals for north, south, east, and west from a selected scenario and random seed. We run two controllers against exactly the same generated arrival sequence: fixed timing changes phase after twenty seconds of green, while adaptive timing considers queue pressure after a minimum of twelve seconds and caps green at thirty-eight seconds. Yellow and all-red intervals are included. This controller changes only virtual signals inside the model; no real traffic hardware is connected.

The worker records run totals, sampled queues, signal state, lane counts, and the reasons for each phase change in four separate MySQL tables. The page displays the junction, a queue chart, actions, and the fixed-versus-adaptive result. This pair has finished in MySQL. The demand fingerprints and arrival counts match, so the two control results are comparable. I will report the actual measured difference displayed here.The model and database-writing path are implemented, and pure model tests passed. The browser-to-MySQL simulation run is still being verified, so the live result is not yet a confirmed database demonstration.

The pure model with seed 42 shows adaptive control reducing experienced wait for both surge scenarios, but doing worse for balanced demand. That is useful: the project compares strategies rather than declaring one universally superior. These generated results do not estimate live Bangalore traffic.

The Kaggle CSV provides dated, aggregated traffic readings. The inspected file has 33,072 data rows, 18 columns, eight areas, and sixteen logical road locations.

src/lib/traffic/core.mjs handles quoted CSV fields and validates dates, categories, nonnegative numbers, and required source columns. It records rejected rows and duplicates.

Show: Import quality report. A parser pass does not prove a MySQL load.

3. MySQL schema

sql/001_schema.sql defines the historical tables, keys, indexes, and checks. Area → Road → Road Segment → logical Sensor → Observation is the principal relationship.

Show: Schema Explorer or Workbench relationships.

4. Import and active dataset

scripts/import-dataset.mjs uses the file SHA-256 to identify an import, inserts validated rows in batches, activates the import transactionally, and refreshes the daily summary.

Show: Workbench count and dataset_import only after a successful run.

5. Original-field trace

Each observation retains a source_data JSON copy of the 18 original field values. This lets a JSON query connect normalized columns back to a source row.

Show: “Original source fields” SQL exercise.

src/app/api/traffic/route.ts receives filter and action requests. src/lib/traffic/service.mjs performs the SQL analysis, while the MySQL driver manages connections.
